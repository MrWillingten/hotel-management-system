1. Introduction

Checkpoint 2 asks for an initial working prototype written with Python functions and collections. This prototype implements the core of the hotel described in the CP1 analysis using only functions and Python's built-in collections – dict, list, tuple and set. It has no classes, no database and no web interface: those belong to the next checkpoints (CP3 and CP4).

The prototype follows CP1 directly. Its data mirrors the entities and the ER diagram, each function enforces business rules from section 3 of CP1 and names them in a comment, and the acceptance scenarios of CP1 section 2.6 are run with the same rooms, dates and amounts.

2. Data structures

2.2 Money and dates

Amounts are whole numbers of millimes (1 DT = 1000 millimes), never floating-point numbers, so 0.1 + 0.2 rounding errors cannot happen (BR24). Dates use datetime.date from the standard library, and a stay is the half-open range [arrival, departure): the departure day is not a night (BR13, BR14). Amounts typed by the user are read as text:

def dinars(text: str) -> int:
    """'150' or '12.500' -> millimes. Parsed as text, never as a float."""
    text = text.strip()
    whole, _, fraction = text.partition(".")
    if not whole.isdigit() or (fraction and not fraction.isdigit()) or len(fraction) > 3:
        raise ValueError(f"'{text}' is not an amount in dinars (e.g. 150 or 12.500).")
    return int(whole) * 1000 + int(fraction.ljust(3, "0"))

3.2 Two stays overlap (BR13)

def overlaps(arrival1: date, departure1: date, arrival2: date, departure2: date) -> bool:
    """BR13: half-open intervals overlap iff a1 < d2 and a2 < d1."""
    return arrival1 < departure2 and arrival2 < departure1

A guest leaving on the 14th and another arriving on the 14th do not overlap.

3.3 Is a room free? (BR3, BR5, BR18)

def is_free(hotel, room, arrival, departure, ignore=None) -> bool:
    if not get_room(hotel, room)["in_service"]:
        return False
    for night in each_night(arrival, departure):
        entry = hotel["room_nights"].get((room, night))
        if entry is None:
            continue
        # A maintenance night has no reservation_id: it is never "this reservation".
        if ignore is None or entry.get("reservation_id") != ignore:
            return False
    return True

One dictionary look-up per night. ignore lets a reservation that changes its dates ignore its own nights (BR18).

3.4 The cancellation fee (BR11 and decision Q2)

def late_fee(hotel, reservation, now) -> int:
    arrival_time = datetime.combine(reservation["arrival"], CHECK_IN_TIME)   # 14:00
    if arrival_time - now >= CANCELLATION_WINDOW:   # 48 hours; exactly 48:00 -> no fee
        return 0
    return accommodation(hotel, reservation["id"]) * CANCELLATION_FEE_PERCENT // 100

Integer arithmetic on millimes: 20 % of 300 DT is exactly 60.000 DT.

3.5 The reservation life cycle (BR16)

TRANSITIONS = {
    "CONFIRMED": {"CHECKED_IN", "CANCELLED", "NO_SHOW"},
    "CHECKED_IN": {"CHECKED_OUT"},
}

def set_status(reservation: dict, new_status: str) -> None:
    if new_status not in TRANSITIONS.get(reservation["status"], set()):
        raise ValueError(f"A {reservation['status']} reservation cannot become {new_status}.")
    reservation["status"] = new_status

Any change that is not in the dictionary – for example checking out a guest who never checked in – is refused with a clear message.

5.1 A bug found by the scenarios

The first version of is_free compared the night's reservation with the reservation to ignore using entry.get("reservation_id") != ignore. For a night closed for maintenance, the entry has no reservation, so get returned None; when no reservation was to be ignored, ignore was also None, and None != None is False. The night was therefore treated as free, and a room under maintenance could be booked – breaking BR5.

The first scenario (room 204 closed for maintenance) failed and revealed it. The function now skips empty nights explicitly and treats any other taken night as an obstacle unless it belongs to the reservation being changed (section 3.3). This shows why each rule is checked by a scenario, not only by trying the menu by hand.

6. Towards CP3

The prototype shows that the rules work. Its limits are also visible: any part of the program can change any dictionary, a misspelt key such as "arival" is only discovered when the code runs, and the rules about a reservation are spread over several functions. The object-oriented design of CP3 answers these points by grouping each kind of data with the rules that protect it:

In the prototypeIn the object-oriented design (CP3)
A reservation dict + set_status, TRANSITIONSA Reservation class whose methods allow only valid changes of status
nights(), overlaps(), each_night()A StayPeriod class (arrival, departure) with these operations
Integers of millimes + dinars(), fmt()A Money class that cannot be mixed up with a plain number
bill() building a dictA bill built by a function from objects, then frozen in an invoice
room_nights keyed by (room, night)The same idea as a database table whose primary key is (room_id, night) in CP4

The same business rules, scenarios and numbers will be reused, so each checkpoint can be compared with the previous one.
